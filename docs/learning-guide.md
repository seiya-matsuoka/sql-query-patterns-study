## 目的と学び方

目的は、SQL の重要な構文・機能を実用的に読み、複数の記述を比較して使い分けられるようになることと、Codex 主体の教材作成・検証・学習支援の運用を試すことである。
基本的な `SELECT`、`WHERE`、`JOIN`、`GROUP BY`、集約関数、サブクエリの知識を前提とする。
必要な基礎事項は各例で再説明し、前提知識があるという理由だけで処理の段階を省かない。

本人は、次の順で学習する。

1. 完成済み SQL を読む。
2. SQL コメントと必要な補足を読み、問い・構文・処理・採用理由を確認する。
3. コマンドまたは GUI で実行結果を確認する。
4. 複数の書き方を比較し、同等になる条件と結果が異なる条件を理解する。
5. 疑問を質問し、必要な補足を確認して、学習状況を伝える。

SQL の自力実装や穴埋め演習は採用しない。
Codex が完成済み SQL、コメント、必要なデータ・期待結果・補足を作成し、許可範囲内で検証・修正する。
本人の学習完了は本人が判断し、教材の作成・検証・レビュー完了とは別に記録する。

## カリキュラム

学習順序は次の 4 区分とする。
CASE 式とウィンドウ関数を中心に、実用例・採用理由・代替記述との使い分けまで厚く扱う。

| 順序・区分                    | 重み付け       | 到達目標                                                               |
| ----------------------------- | -------------- | ---------------------------------------------------------------------- |
| 1. CASE・条件付き集約・FILTER | 厚め           | 条件による値の選択と集約対象への影響を説明し、用途に応じて記述を選べる |
| 2. EXISTS / NOT EXISTS        | 標準           | 存在・非存在の問いを読み取り、他の記述との同等性・相違を説明できる     |
| 3. CTE・再帰 CTE              | 標準〜やや厚め | 段階的な問い合わせを読み、再帰の各反復で生成される行と終了条件を追える |
| 4. ウィンドウ関数             | 厚め           | 行を残す集計、順位、前後行、計算範囲を理解し、代替記述と使い分けられる |

### 1. CASE・条件付き集約・FILTER

- 単純 CASE と検索 CASE、分類の境界、条件が重なる場合の優先順位、NULL・未知の区分の扱い。
- `SELECT`、`ORDER BY`、`GROUP BY`、`WHERE`、`HAVING` など、式を置く各句での役割。
  条件を直接記述する方法とも比較し、CASE を使う理由を示す。
- 金額帯などによる分類・集計、業務上の表示順、顧客区分などに応じて変わる基準値。
- `UNION ALL` を使った売上・返金の集計と、CASE・条件付き集約を使う整理。
  元データの粒度と符号、重複、集約単位を揃え、比較が成立する条件を説明する。
- 複数の条件別指標を同じ問い合わせで求める方法。
- `COUNT`・`SUM`・`AVG` と、CASE の戻り値・ELSE・NULL が集約対象に与える影響。
- CASE、集約ごとの `FILTER`、問い合わせ全体の `WHERE` の違いと使い分け。

初回は、CASE と FILTER による条件付き件数・合計の同等比較から始める。
該当なし、NULL、ELSE の扱いで結果が異なる比較も含める。
初回の試行教材も、検証後は正式な学習対象として進捗文書の教材一覧へ登録する。

### 2. EXISTS / NOT EXISTS

- 該当する注文がある顧客を、`JOIN + DISTINCT` と `EXISTS` で求める。
  顧客の重複、同名の別顧客、結果の 1 行の意味を比較する。
- 注文自体がない顧客と、条件に該当する注文がない顧客を区別する。
- `LEFT JOIN + IS NULL` と `NOT EXISTS` を比較する。
  JOIN 条件の位置と、NULL 判定に使う列の非 NULL 性を説明する。
- `IN / NOT IN` と `EXISTS / NOT EXISTS` を、NULL・空集合を含む少量の専用データで比較する。
  「等しい行がない」と、NULL により真偽が不明になる場合を区別する。

### 3. CTE・再帰 CTE

- 派生表と CTE を比較し、名前付けと読み進める順序を考える。
- 顧客別集計、分類、再集計へ進む段階的な問い合わせを読む。
  CTE にしただけで高速になると説明しない。
- 簡単な整数列で、開始部分・再帰部分・反復・終了条件を理解する。
  各反復の入力と生成行を、小さな表で追えるようにする。
- 指定カテゴリ自身と子孫を、深さ付きで取得する有限の階層例を読む。
  基準となるカテゴリを含む理由、枝分かれ、終了の前提を説明する。

高度な再帰の網羅を目的にせず、SQL を読みながら行の流れと結果を説明できることを目指す。

### 4. ウィンドウ関数

- 集約結果を JOIN する方法と、集約ウィンドウ関数で明細行を残す方法を比較する。
- グループ内の合計・平均・構成比と、分母・NULL・該当なしの意味を確認する。
- `ROW_NUMBER`、`RANK`、`DENSE_RANK` を用いた順位・上位抽出で、同順位の扱いと必要な結果件数を区別する。
- 最新行の取得で、同日時、ID と日時順の不一致、採用する 1 行の決め方を扱う。
  上位抽出と同じ構文でも、異なる判断を学ぶ問いとして残す。
- 自己結合・相関サブクエリなどと `LAG / LEAD` を比較し、前後行・端の行・日付の欠けを観察する。
- 累積集計、`ROWS` と `RANGE`、同順位によるフレームの違い、移動集計を扱う。
  行数と日付間隔を同一視しない。
- 集約ウィンドウ関数と FILTER の組み合わせは、必要な問いで扱う。
  第1区分の説明を参照しつつ、理解に必要な再説明は残す。

### 比較と分割の共通方針

標準 SQL を優先し、同等な書き換えと、結果の違いを学ぶ比較を区別する。
NULL、重複、同順位、並び順、該当なし・入力なしを必要なデータで観察する。
短さ・可読性・性能を区別し、未実測の性能は性能未評価とする。
実行計画の体系的な学習は今回の区分へ追加しない。

ファイル数や SQL 文数は固定しない。
異なる使い分けを学べる問いは残し、同じ問いの境界条件は関連する比較としてまとめる。
問いと結果を追いやすい単位で分割・統合し、説明を削るための統合や、見た目だけを変えた大量の例は作らない。

## コメントと補足の基準

SQL コメントを説明の中心にし、問い、入力の前提、結果の意味、処理、採用理由、比較条件、注意点を十分に説明する。
必要な説明を既知と推測して省かず、理解に役立つ再説明を残す。
コードを日本語で読み上げるだけのコメントや、目的のない全文再掲は避ける。

### コメント基準例（未実行）

次のコードは、説明の粒度を合わせるための未実行の見本である。
件数と合計は入力から導いた予測であり、実測結果・期待 CSV・検証済み教材ではない。
`WITH` はこの見本の 3 行を `sample_orders` という名前で参照するために使い、共通テーブルを必要としない。

```sql
-- example: paid-count-and-total-comparison
-- 問い：支払済みの注文件数と、金額が分かる注文の合計を CASE と FILTER で比べる。
-- 入力は 1 行 1 注文で、paid は支払済み、unpaid は未払いを表す。
-- 支払状態と金額の判明状況は別であり、金額が NULL でも支払済みの注文は存在する。
-- 結果は入力全体を集約した 1 行で、件数の比較 2 列と合計の比較 2 列を持つ。
WITH sample_orders (order_id, status, amount) AS (
    VALUES
        (1, 'paid', CAST(100 AS DECIMAL(10, 2))),
        (2, 'paid', CAST(NULL AS DECIMAL(10, 2))),
        (3, 'unpaid', CAST(200 AS DECIMAL(10, 2)))
)
SELECT
    -- COUNT(式) は式の値が NULL でない行を数える。
    -- 支払済みなら金額ではなく 1 を返し、金額 NULL の注文も件数に含める。
    -- ELSE の省略時は、どの WHEN も真でなければ NULL となり、未払いを数えない。
    COUNT(CASE WHEN status = 'paid' THEN 1 END) AS paid_count_case,

    -- FILTER は、この集約関数に渡す行だけを条件で絞る。
    -- COUNT(*) は絞った後の行を数えるため、金額が NULL でも除外しない。
    COUNT(*) FILTER (WHERE status = 'paid') AS paid_count_filter,

    -- SUM は NULL でない値を合計する。
    -- CASE は支払済みの金額を返し、未払いは ELSE 省略により NULL にする。
    -- 支払済みの金額 NULL も合計には寄与せず、不明な金額を 0 と確定したわけではない。
    SUM(CASE WHEN status = 'paid' THEN amount END) AS paid_total_case,

    -- CASE が集約へ渡す値を選ぶのに対し、FILTER は集約へ渡す行を選ぶ。
    -- 行を絞った後も SUM の NULL の扱いは同じであり、この CASE 版と同等になる。
    SUM(amount) FILTER (WHERE status = 'paid') AS paid_total_filter
FROM sample_orders;
```

予測する件数は両方 `2`、合計は両方 `100.00` である。
ここでの合計は、支払済みの金額すべてが判明した総額を保証するものではない。
`COUNT(CASE WHEN status = 'paid' THEN amount END)` にすると、金額が判明している支払済み注文の件数 `1` を数え、問いが変わる。
COUNT の CASE に `ELSE 0` を付けると、0 も非 NULL なので未払いまで数える。
SUM の CASE で ELSE を省略する方法と `ELSE 0` を使う方法は、該当なし・金額がすべて NULL などで差が出るため、一律に同等と扱わない。
非 NULL の集約対象がないときの SUM は NULL となり、0 と区別する。
これらの集約の意味は [PostgreSQL 18 の集約関数](https://www.postgresql.org/docs/18/functions-aggregate.html) を参照する。

この例では、同じ入力に対して件数同士・合計同士を比較するため、CASE 版と FILTER 版を同じ結果の行に並べた。
問い合わせ全体へ `WHERE status = 'paid'` を付けると、同じ SELECT にある他の集約も支払済みの行だけを対象にする。
FILTER は各集約に個別の条件を付けられるため、全注文と支払済み注文などを同じ問い合わせ内で集計するときに適する。
CASE と FILTER の役割は [条件式](https://www.postgresql.org/docs/18/functions-conditional.html#FUNCTIONS-CASE) と [集約式の FILTER](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-AGGREGATES) の公式説明を参照する。
この見本の説明量を最低ラインの目安にし、実教材では問いに応じて処理途中や代替記述の採用条件も補う。

## データの初期設計

| データ                   | 基本の内容・粒度                                         |
| ------------------------ | -------------------------------------------------------- |
| `customers`              | 顧客 ID、表示名、顧客区分。1 行 1 顧客                   |
| `orders`                 | 注文 ID、顧客 ID、注文日時、状態、注文金額。1 行 1 注文  |
| 売上・返金の専用データ   | 集計単位や符号、UNION ALL と CASE の比較に必要な少量の行 |
| カテゴリ階層の専用データ | 指定カテゴリ自身と子孫、深さ、枝分かれを追える小さな階層 |
| NULL 比較の専用データ    | NULL と空集合による存在判定・比較の相違を観察する行      |

ID は整数、金額は DECIMAL、日時は固定値とし、現在日時や乱数に依存させない。
共通テーブルの主キー・外部キーなどの制約を壊さず、NULL が意味を持つ非キー列や専用データで境界を表現する。
データ件数を固定目標にせず、処理途中と結果を追える小ささを優先する。
専用データは、その教材を作成するときに追加する。

必要な問いで、次の条件を観察できるようにする。

- 分類境界と等しい値、条件の重なり、未知の区分。
- 該当なし、入力なし、集約対象の値がすべて NULL。
- 該当注文が複数ある顧客、注文のない顧客、同名の別顧客。
- 同額、同日時、ID と日時順の不一致、欠けた日付、1 行だけのグループ。
- 長さの異なる枝と複数の子を持つ、有限で循環のない階層。

共通データを変更する場合は、影響する教材と期待結果を特定し、必要な回帰検証を行う。
専用データだけで扱える違いを、共通データの不自然な変更で表現しない。
NULL の出力表記に使う `<NULL>` は、文字列データの値として使用しない。

| `bash scripts/study.sh stop`                 | 専用環境を停止し、データボリュームを保持する                 |

`reset-data` は既存の学習用データを再構築する明示的な操作とし、許可された対象に限定する。
`start`、`run`、`verify` に学習用スキーマ・データの自動初期化・再構築を組み込まない。
初回の専用 PostgreSQL インスタンスの初期化と、教材データを `reset-data` で用意する操作を区別する。
通常の教材実行は読み取りを基本にし、未準備であれば不足を報告する。

### 問い合わせごとの照合設計

1. 各問い合わせの前に `-- example: paid-count-case` のような識別子を置く。
   同一教材内で重複させず、教材のパスと識別子で期待 CSV を一意に対応付ける。
2. 各区切りを、CTE や UNION を含み得る 1 つの完結した問い合わせとする。
   識別子は抽出のための最小限の記法とし、説明の量・構成を一律にするテンプレートにはしない。
3. `run` は教材ファイル全体を実行し、`verify` は同じ教材から対象 SQL をそのまま取り出して実行する。
   検証専用の別 SQL を正本にしない。
4. 列名を含む CSV で照合し、0 行の結果も列名を持つ結果として扱う。
   空ファイル、空文字の値、NULL を持つ行、データ行が 0 件の結果を区別する。
5. 検証出力の NULL 表記を `<NULL>` に固定し、UTF-8・LF・日時などの出力条件を揃える。
   空文字・0・NULL の置換、重複除去、並べ替え、数値丸めで差を隠さない。
6. 複数行の結果の安定した順序は、教材 SQL の最終 `ORDER BY` で定める。
   ウィンドウ関数内部の計算順と、最終結果の表示順を分けて説明する。
7. SQL エラー、接続失敗、期待結果の欠落、結果不一致を失敗として返し、対象と原因・差が分かる形で報告する。
8. 期待結果は入力データと要件から独立に導出する。
   実行結果からの自動更新や、不一致を消すだけの書き換えは採用しない。
9. 型が学習上重要な例は、CSV の一致と別に確認する。
   CSV の一致を、型やあらゆる入力に対する同等性の証明とは扱わない。

psql の CSV 出力・標準入力からのファイル実行・エラー停止を利用する設計とする。
`ON_ERROR_STOP` による停止や終了状態の伝達などは、第2工程で実装・確認する。
機能の根拠は [PostgreSQL 18 の psql 公式仕様](https://www.postgresql.org/docs/18/app-psql.html) を参照する。
初期段階では、独自の SQL パーサーや専用テストフレームワークを導入しない。
最小限の区切り抽出と実教材で受入条件を満たせない場合は、問題・代案を提示し、未検証の方式を後続へ展開しない。

## 作業サイクルと受け渡し

| 段階            | 担当と実施内容                                                                    | 次への条件・停止地点                                                   |
| --------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |

| 指摘対応        | 制作担当が指摘を修正する                                                          | 結果・意味・共通データに影響する変更は回帰検証と必要な再レビューを行う |
| `main` への反映 | Codex がコミット・PR の文案を用意し、本人が差分と確認結果を見て取り込む           | 受入条件と必要な確認を満たした教材を学習に渡す                         |
| 本人の学習      | 本人が `main` の教材を読み、実行結果を確認し、質問する                            | Codex は説明し、依頼範囲内で補足へ反映する                             |

毎回の自己確認と、別チャットによる独立レビューを区別する。
レビューでは、説明品質、重要な内容の網羅、例の適切さ、入力・SQL・コメント・結果の対応を重視する。
実行の許可範囲は依頼に明記し、読み取り専用レビューをファイル修正へ拡張しない。
本人から対象を指定した先行生成の依頼がある場合は、その範囲だけ扱う。

Git・GitHub の操作は本人が行うことを基本とする。
Codex は操作する段階に合わせて、Issue のタイトルと本文、ブランチ名、コミット件名、PR のタイトルと本文を用意する。
合意済みの目的や実際の差分・確認結果を埋めた形で提示する。
作業単位、文案の内容、マージの条件は `AGENTS.md` に定める。

### 次のプロンプト案の運用

本人の全学習終了まで、原則として毎回答の最後に次のプロンプト案を提示する。
送信先を明記し、既知の対象・状態・確認結果・残件・許可範囲・停止地点は Codex が埋める。
本人の意見が必要な部分だけ、選択肢付きの記入欄にする。
未記入を承認や学習完了として扱わず、提示だけで次の作業を開始しない。

| 回答時点                     | 次の依頼と送信先の基本方針                                                       |
| ---------------------------- | -------------------------------------------------------------------------------- |
| 第1工程の文書を確定した      | 文書の確認・修正、または `main` の初回公開の準備を依頼する                       |
| `main` の初回公開を確認した  | 第2工程の作業単位を示し、着手に使う Issue 文案とブランチ名を用意する             |
| 初回教材の作成・検証が済んだ | 新しいレビュー用チャットへ、実在する対象・確認結果・レビュー範囲を渡す           |
| レビューで指摘が出た         | 現在の制作担当チャットへ具体的な指摘を渡す。必要なら新しい制作チャットへ引き継ぐ |
| コミット・PR を準備する      | 文案と実際の検証状況を示し、マージ前に必要な確認を伝える                         |
| 教材を `main` に取り込んだ   | 学習を担当する通常チャットへ、対象・実行方法・確認範囲を示して渡す               |
| 疑問へ説明・補足を追加した   | 解消した／まだ不明／別の疑問、を選んで続けられる依頼文にする                     |
| 本人が学習完了を申告した     | 進捗更新と次の対象の依頼を用意し、通常チャットを切り替えるかも判断する           |
| 未解決の失敗・不足がある     | その問題の調査・修正・必要な判断を依頼する。後続教材へ進めない                   |
| 本人が全学習終了を申告した   | ルート README の作成を依頼する文章を用意する                                     |

同じ対象の判断経緯が役立つ場合は同じチャットで継続する。
作業目的の変化、自然な区切り、必要な文脈の変化、過去の試行の蓄積、論点の混在、本人の希望から、Codex が新しい通常チャットへの切り替えを判断し、理由を短く示す。
発言回数や工程だけで固定せず、独立レビューへの受け渡しとも区別する。

新しいチャットへの非公開の引き継ぎでは、ファイルに未反映の合意、実施済み・未実施、残件、既存変更、確認時点の状態、有効な許可、次の対象・受入条件・停止地点を本文へ要約する。
直前の引き継ぎ元と、必要な過去チャットのリンク欄を用意し、取得できる正確なリンクは Codex が埋める。
取得できないリンクだけ本人の記入欄を残し、追加リンクには参照目的を付ける。
リンクの自動伝達を前提にせず、本文と現物だけでも開始できるようにする。
引き継ぎ先では閲覧可否と現在のファイル・Git・必要な環境状態を再確認し、重要な不足だけを質問する。
許可は同じ対象・操作の範囲で引き継ぎ、過去の許可を別操作へ拡張しない。
引き継ぎ後は新しい制作担当を明確にし、旧チャットと同時に同じファイルを変更しない。

## 実施工程と受入条件

### 第1工程の文書確定

第1工程の対象は `AGENTS.md` と本書の 2 文書とし、初期計画と継続的な作業ルールを整理する。
初期計画と実績の記録先、コメント基準例、Git・GitHub の運用、チャット運用の責務を定める。
受入条件は、両文書の内容と参照先が整合し、公開可能な情報で計画を読めることである。
文書の自己確認結果を報告し、本人の確認・次の依頼を待つところで停止する。

### 文書確定後の `main` の初回公開

本人による文書確認後に、初回公開の作業としてローカルの Git 状態と GitHub の公開先を確認する。
初期計画と作業ルールの 2 文書を公開対象とし、相対パスと公開可能な情報で記述されていることを確認する。
Codex は必要なコミット件名と操作手順を用意し、本人が確定した文書を `main` へ反映して公開する。
公開された `main` を GitHub の既定ブランチとし、後続の作業ブランチの起点と PR の取り込み先にする。

### 第2工程の環境・初回教材・検証の整備

`main` の初回公開の確認と、本人による具体的な実施依頼の後に開始する。
専用 Compose 環境、固定データ、Git Bash の入口、両 GUI、最初の条件付き集約教材、問い合わせごとの期待 CSV を対象にする。
環境から教材の照合までを一緒に確認できるよう、1 Issue・1 作業ブランチ・1 PR にまとめる。
この工程で `docs/learning-status.md` を作成し、実在する教材と確認済みの手順、検証結果、残件、進捗を記録する。
初回の実動で、次の受入条件を実際に確認する。

| 対象           | 確認する内容                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------- |
| 実行基盤       | 起動、明示的なデータ準備、個別実行、個別・一括検証、データを保持した停止                        |
| GUI            | 両方で同じ DB へ接続し、個別・複数の問い合わせと結果表を確認する。同時有効時の干渉も確認する    |
| 結果照合       | 複数の問い合わせ、0 行、NULL、空文字、重複、順序を区別する                                      |
| 失敗検知       | SQL エラーと既知の結果不一致を失敗として返す。接続失敗・期待結果欠落も成功扱いしない            |
| 期待結果の保護 | 失敗時も期待 CSV を自動更新しない                                                               |
| 初回教材       | CASE/FILTER の同等比較と、該当なし・NULL・ELSE による差を、説明・入力・予測・実結果で対応付ける |
| 進捗文書       | 実在する教材への相対リンク、確認済みの手順、確認結果、未確認事項を記録する                      |
| 受け渡し       | 対象、確認結果、未確認事項、レビュー範囲を埋めた次のプロンプト案を提示する                      |

検証補助自体の確認に必要な例と、本人が学ぶ正式教材を区別する。
検証のための例をすべて学習課題へ追加する必要はない。
GUI の本人確認が未完了なら、進捗文書と PR に確認待ちとして記録する。
初回教材は必要な確認と独立レビューを経て `main` に取り込む。
本人が学習し、読後の反応を踏まえて次の対象を依頼する。

### 第3工程の教材作成と学習

合意した学習順序に沿い、少数の関連する問いごとに、作成・検証・必要な独立レビュー・本人の学習・補足を反復する。
一緒に確認して学習へ渡せる問いを、原則として 1 Issue・1 作業ブランチ・1 PR の作業単位にする。
たとえば CASE の分類・優先順位・業務順は一つの単位にできる。
ウィンドウ関数は、順位・最新行、累積・移動集計など、確認する判断のまとまりごとに分ける。
小さくまとまる区分は、区分全体を一つの作業単位にできる。
区分の区切りでは、到達目標の充足、例の過不足、説明の不足・重複を確認する。
共通データ・実行補助の変更時は、影響する既存教材を再検証する。
再帰 CTE の反復、同順位・最新行・前後行・フレーム境界を重点確認し、一律のテスト数や文書量は要求しない。

### 第4工程のルート README

本人の全学習終了の申告と作成依頼を受けて開始する。
リポジトリ全体を案内する文書整備として、独立した作業単位にする。
実際に完成した内容から、目的、扱った内容、教材への入口、使用技術、本書と進捗文書への案内を記載する。
新しい学習対象や公開工程を自動で追加しない。
