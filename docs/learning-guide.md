# SQL 応用学習ガイド

本書は現在有効な学習目的、カリキュラム、教材・説明・データの選定基準を定める。
制作と操作の規則は [AGENTS.md](../AGENTS.md)、実在する教材・実行手順・確認結果は [学習状況](learning-status.md) を参照する。
合意した方針変更は既存の記述を置き換え、古い計画との併記や例外の追加を続けない。

## 目的と学び方

初級脱出と中級へのステップアップを目指し、実務的な問いに対して SQL の構文と書き方を選べるようになる。
SELECT・WHERE・JOIN・GROUP BY・集約関数・サブクエリの基本知識を前提とする。
構文を使う場所や書ける変形を網羅すること、教材数や説明量を増やすことは目的にしない。

本人は完成済み SQL とコメントを読み、普段使う GUI または run で結果を確認し、必要な比較を読む。
自力実装・穴埋め・クイズは必須にしない。
疑問はチャットで解消し、本人が伝えた学習状態を記録する。
一括で制作された区分も、学習時には任意のまとまりで読み進めてよい。

## カリキュラムと完了条件

次の順序を維持し、CASE とウィンドウ関数は実用例と採用判断を厚く扱う。
各区分の着手時に到達目標・業務の問い・主例・必要な比較を対応付け、その範囲をまとめて完成させる。
範囲を満たした後に、構文変形を思い付くたびに例を追加しない。

### 1. CASE・条件付き集約・FILTER

到達目標は、条件による値の選択と集約対象への影響を説明し、用途に応じて記述を選べることである。

- 単純 CASE と検索 CASE、境界・優先順位、NULL・未定義区分を扱う。
- 分類、業務上の表示順、分類別集計、条件別の件数・合計・平均を業務の問いへ結び付ける。
- CASE・FILTER・問い合わせ全体の WHERE を、対象と結果の粒度から使い分ける。
- 区分別基準による注文抽出と顧客合計判定を、直接条件、WHERE・HAVING の違いと比較する。
- 売上・返金の純額を、同じ明細粒度・符号・重複の扱いで CASE と UNION ALL により比較する。

学習済みの 01～09 は維持し、未学習の 10～12 の一括制作で残りを完成させる。
第1区分の本人の学習完了は、残りの学習についても本人の申告を受けて判定する。

### 2. EXISTS / NOT EXISTS

到達目標は、存在・非存在の問いを読み取り、他の記述との同等性と相違を説明できることである。

- 該当注文がある顧客を、EXISTS と JOIN + DISTINCT で比較する。
- 注文自体がない場合と、条件に該当する注文がない場合を区別する。
- NOT EXISTS と LEFT JOIN + IS NULL を、JOIN 条件の位置と判定列の非 NULL 性から比較する。
- IN / NOT IN の NULL・空集合を含む比較で、等しい行がない場合と判定が不明な場合を区別する。

### 3. CTE・再帰 CTE

到達目標は、段階的な問い合わせと再帰の開始・反復・終了を追えることである。

- 顧客別集計・分類・再集計を、派生表と CTE の名前付け・読み進める順序から比較する。
- 小さな整数列で再帰の開始と反復を示し、カテゴリ階層の取得へつなぐ。
- 指定カテゴリ自身と子孫、深さ、枝分かれを扱い、有限で循環しない前提を明示する。

高度な再帰の網羅や、CTE にするだけで高速になるという説明は行わない。

### 4. ウィンドウ関数

到達目標は、行を残す集計、順位、前後行、計算範囲を理解し、代替記述と使い分けられることである。

- 集約結果との JOIN とウィンドウ集計を比較し、合計・平均・構成比の対象と分母を明示する。
- ROW_NUMBER・RANK・DENSE_RANK による上位抽出と最新行の取得で、同順位と一意な行の選択を区別する。
- LAG / LEAD を自己結合などと比較し、端の行と日付の欠けを扱う。
- 累積・移動集計で ROWS・RANGE と同順位による計算範囲を比較する。

表示順の安定化と計算上の同順位を分け、日時の同値・ID と日時順の不一致を必要な入力で観察する。

## 主例と比較の選び方

業務の問いごとに、要件を満たし読みやすい主例を先に置く。
CASE は分類・優先順位・条件付き集約・基準値の選択など、値を選ぶ理由があるときに使う。
直接条件や FILTER が適切なら、それも選択肢として示す。
固定規則の SQL 記述と、規則をデータとして管理する方法は、条件数・変更頻度・重複から判断し、単純な例に不要な仕組みを追加しない。

比較を残す条件は、採用判断または誤りの理解が一つ増えることである。
同じ判断の構文違い・境界違いは関連する例へまとめる。
比較には「同等な代替記述」「要件が変わる比較」「当該要件では採用しない例」の位置付けを明記する。
同等性は入力・条件・NULL・重複・粒度・順序の成立条件と合わせて説明する。

不要な多段化、規則の繰り返し、意味のない集約を主例へ持ち込まない。
性能未測定を、それらを許容する理由にしない。
小さな入力での結果一致から実テーブル上の性能を断定せず、性能未評価という状態は検証記録に一度示す。
実行計画の体系的な学習を新しい区分として追加しない。

## コメントと補足の基準

コメントは、問いの意図と構文の読み方・役割・採用理由を中心にする。
誤読すると結果が変わる粒度・NULL・境界などは、必要な場所で説明する。
行数の上限・下限や、説明量の最低ラインは設けない。

HAVING の主例では、次のように意図と書き方を結び付ける。

```sql
-- 問い：支払済みの判明合計が、顧客区分別の基準以上となる顧客を選ぶ。
-- CASE は区分に応じた基準値を返し、HAVING で SUM(amount) と比較する。
-- WHERE は合計する注文の状態を、HAVING は集計後に残す顧客を決める。
```

新出構文の読み方は初出で説明し、後の比較は変わる箇所と理由を説明する。
SELECT から順に処理を日本語へ置き換える説明、全列・全入力行・期待値の網羅的な再掲、同じ前提の繰り返しは避ける。
具体的な数値や行は、条件位置の誤りなどを理解する決定的な一例に絞る。
ファイル保護や検証方式といった運用説明は SQL に繰り返さない。

補足は、図・対応表・複数の例を結ぶ概念説明が必要な場合だけ作る。
コメントを削った分を補足へ移して総量を維持したり、質問のたびに会話の経緯を追記したりしない。
SQL 自体の誤りは本体で修正し、補足だけで済ませない。

## 入力と期待結果

主な業務例は小さな共用の実テーブルを使い、顧客と注文などの関係を SQL から読み取れる形にする。
同じ業務データを各問い合わせの FROM に再掲しない。
VALUES は数行の NULL 比較や再帰の開始値など、値そのものを示す必要がある場合に限る。

学習済み 01～09 は従来の入力を維持する。
初回の固定データは study スキーマで保護し、10 以降の業務例は practice スキーマを使う。
後続で必要な日時・同順位・階層などのデータは、その区分の制作に含めて追加する。
主キー・外部キーの制約を壊して境界条件を作らず、共有入力の変更は依存する教材と一緒に回帰検証する。

ID と入力は固定し、現在日時や乱数に依存させない。
金額は DECIMAL を使い、NULL・0・空文字・0 行を区別する。
期待 CSV は各問い合わせの入力と要件から実行前に導出し、教材 SQL をそのまま実行する verify で照合する。
結果の丸め・並べ替え・重複除去・NULL の置換で差を隠さず、型が重要なら CSV の一致とは別に確認する。

## 制作と学習のサイクル

1. 区分全体の範囲を決め、完成済み SQL・必要なデータ・期待 CSV をまとめて制作し、自己確認と許可された実行検証を行う。
2. 別チャットで独立レビューを 1 回行い、指摘があれば制作担当が修正し、影響する範囲を再確認する。
3. CLI 検証と独立レビューの結果を揃え、本人が 1 PR として main に取り込む。
4. 本人が普段使う GUI または run で学習し、疑問と学習状態を伝える。

GUI の学習時確認と、制作側の CLI 検証・独立レビューを区別する。
取り込み前に両 GUI で全問を確認することは要求しない。
作成・検証・レビューの完了から、本人の学習完了を推測しない。

原則として毎回答の最後に、次の学習・作業へ円滑に進むためのプロンプト案を示す。
通常の質問は同じ学習の文脈で続け、送信先と必要な既知情報を埋めた文章をそのまま送れる形で提示する。
プロンプト案の提示と制作単位の分割は区別し、提示のたびに新しい制作・レビュー・Git 操作の一周を追加しない。
全区分の学習終了の申告と作成依頼を受けた後に、実在する教材を案内するルート README を作る。
